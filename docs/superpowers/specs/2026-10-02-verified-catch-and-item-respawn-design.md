# 联机身份码抓捕与场地道具刷新设计

**日期：** 2026-10-02
**状态：** 待用户审阅
**目标：** 联机抓捕必须经过鼠方现场出示一次性个人码、猫方手动核验；共享道具在已选场地内不定时补充。

## 1. 范围与现状

本次处理浏览器版的真实玩家联机规则。用户确认每只老鼠使用一次性个人码，猫输入核验，并要求完成功能后分别在 Codex 内置浏览器和系统浏览器中测试。

当前自动靠近抓捕只存在于单机 AI 的 `gameTick` 流程；联机客户端只注册 `CATCH_EVENT` 接收器，没有真人抓捕的发起 UI 或网络流程。relay 当前会透传客户端 `CATCH_EVENT`，没有核验码或抓捕者/目标队伍校验。

地图道具客户端会按相同房间种子生成初始道具，并向 relay 请求拾取确认；relay 只保存已拾取 ID。联机重连会恢复已拾取 ID，但没有新增道具的权威状态或刷新消息。

不改定位和位置展示。本次不以 GPS 距离、持续时间或客户端坐标作为抓捕依据。单机 AI 保持原有模拟抓捕行为；本次个人码和服务端刷新规则用于服务器联机房间。

## 2. 用户体验

- 鼠队游戏界面提供“出示抓捕码”操作。点击后向 relay 请求一个新的 6 位数字一次性码，并只在本设备的弹窗中显示。再次请求会让旧码失效。
- 抓捕码有效期为 120 秒；鼠方可重新请求新码。一次有效码最多成功抓捕一次。
- 猫队界面提供“核验抓捕码”操作。猫手动输入对方当面出示的代码并提交。输入错误、过期、已使用、鼠方不在线或活动未开始时只向该猫显示可理解的失败提示，不计为抓捕。
- 核验成功后显示抓捕结果并给猫队本地玩家增加原有成功抓捕积分；所有联机客户端收到同一结果。服务端通过连接绑定的玩家身份确定猫和鼠，不信任客户端传来的队伍、名称或玩家 ID。
- 道具最多同时有 8 个。道具在本局开始时由 relay 在区域多边形内生成；有空位时按随机 30–90 秒间隔补充一个。拾取后，道具从所有客户端移除，并开始等待后续补充。
- 所有客户端通过 relay 收到同一道具的坐标、类型和 ID。初次入局及已加入玩家断线重连时会收到当前存活道具快照；已消费道具不会因重新连接而复活。
- 用户离开联机房、房间到期或活动时间结束后，不再发放个人码或刷新道具。

## 3. 服务端权威流程

### 3.1 一次性抓捕码

relay 维护每个已开始房间的有效抓捕码，映射到由服务端连接状态确认的鼠队玩家和过期时间。`CATCH_CODE_REQUEST` 仅允许已开始房间中的鼠队成员请求；relay 生成不可预测的 6 位数字码，替换该玩家此前未使用的码，并通过私有 WebSocket 消息返回给该玩家，不广播到房间。

猫队玩家发送 `CATCH_CODE_VERIFY`。relay 从连接状态取出抓捕者身份，从服务端码表取得鼠方身份，检查双方处于同一已开始房间、队伍不同且码仍有效。成功时原子消费该码并由 relay 广播 `CATCH_EVENT`，事件含猫/鼠 ID 与显示名称。无效核验只向请求者返回统一错误，不指出代码属于哪位鼠队玩家。relay 将每只猫的失败尝试限制为每 30 秒最多 5 次，并将鼠方发码请求限制为每 2 秒最多 1 次；同时拒绝客户端直接伪造的 `CATCH_EVENT`。

代码不是账号认证或防作弊凭证；房间玩家身份继续沿用当前 client-supplied player ID 的会话模型。一次性码只用于现场人工确认目标并防止 GPS 漂移造成自动抓捕。

### 3.2 道具刷新与房间快照

relay 持有房间的活动区域、存活道具列表、下一个唯一道具 ID、待处理刷新定时器及活动结束时间。开始房间时，在有效区域内采样并生成最多 8 个初始道具；边界采样使用与客户端一致的多边形包含规则。房间没有有效多边形时，不生成场地道具。

`MAP_ITEM_PICKUP` 只在道具 ID 当前存活、请求玩家符合该道具阵营规则时被接受。relay 移除道具并广播拾取人 ID；有空位时安排一次随机延迟刷新。刷新事件包含完整道具对象，客户端只应用 relay 事件，不本地随机创建联机道具。房间状态快照通过 `JOIN_ACK` 提供；开局事件携带初始快照。

刷新定时器必须在活动结束、房间过期或服务端清理房间时停止。掉线期间房间状态留在 relay 内存中；已加入玩家重连恢复存活道具和未过期个人码规则，不恢复已消费码。relay 重启会结束内存中的房间，与当前生命周期一致。

## 4. 网络接口与客户端职责

新增/明确以下消息：

| 消息 | 方向 | 用途 |
| --- | --- | --- |
| `CATCH_CODE_REQUEST` | 鼠客户端 → relay | 请求或刷新自己的个人码 |
| `CATCH_CODE_ISSUED` | relay → 请求鼠客户端 | 私发个人码和过期时间 |
| `CATCH_CODE_VERIFY` | 猫客户端 → relay | 提交猫方输入的代码 |
| `CATCH_CODE_ERROR` | relay → 请求猫客户端 | 单次核验失败提示 |
| `CATCH_EVENT` | relay → 房间全体 | 服务端确认的成功抓捕结果 |
| `MAP_ITEM_SPAWN` | relay → 房间全体 | 新道具完整状态 |

`ROOM_STARTED` 和 `JOIN_ACK` 提供当前道具快照；`MAP_ITEM_PICKUP` 的 relay 广播仍作为权威移除事件。客户端按玩家 ID 应用积分、战绩与反馈，避免重名玩家被误认。离开游戏视图时解绑所有新增事件监听和清理本地待处理 UI 状态。

## 5. 错误处理与约束

- 断线时不显示或假定核验成功；发送失败时 UI 允许重试。已过期或已消费的码需要鼠方重新出示。
- 核验失败不广播给房间、不增加积分或抓捕次数。错误提示避免泄露码属于哪位鼠队玩家。
- 服务端不能从客户端接收任意道具坐标作为刷新权威数据；生成的点必须落在房间多边形内。
- 同一道具只能被 relay 接受拾取一次；重复、伪造、超出当前活动快照的 ID 被忽略。
- 房间无有效区域时关闭刷新，不退回到区域外的矩形随机坐标。
- 单机 AI 对局及其当前计分/模拟抓捕行为不受影响。

## 6. 验收标准

1. 联机猫靠近老鼠或停留任意时长都不会自动触发抓捕。
2. 鼠方点击后只在自己的客户端看见当前 6 位码；猫手动输入有效码后成功抓捕并消费该码。
3. 错误码、过期码、重用码、鼠方自己的码和另一房间的码都不能抓捕或加分；服务端不接受客户端伪造的 `CATCH_EVENT`。
4. 成功结果在同房间所有在线客户端一致；计分、抓捕次数和成就只给正确的猫玩家记账。
5. 联机道具初始、拾取、刷新、重连后存活集合一致；刷新点都在选中多边形内，存活数量不超过 8，且道具不会重复计分。
6. 单机 AI 抓捕流程保持现状。
7. 本地服务启动后，在 Codex 内置浏览器和系统浏览器各完成至少一次双客户端联机流程：创建房间、加入、开始、鼠出示码、猫成功核验及无效码拒绝、道具拾取与刷新，并确认控制台无相关错误。

## 7. 验证范围

- relay 单测覆盖码私发、过期/一次性/队伍检查、伪造抓捕拒绝、道具多边形约束、拾取幂等、定时刷新与快照恢复。
- 客户端和 relay 既有测试套件均运行。
- 使用本地静态 HTTP 服务与本地 relay，不写入生产服务器或生产房间。
- 两种浏览器都执行 UI 联机验证。内置浏览器作为一个客户端，系统浏览器作为另一个客户端；至少再交换一次阵营确认两种身份界面均正常。
- 不把 GPS 精度、定位坐标正确性或部署到线上列入本次验收。
